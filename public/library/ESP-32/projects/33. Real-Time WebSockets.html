Real-Time WebSockets

Hey my brooo 👋

Welcome back! ⚡

You've already built web applications that communicate with your ESP32 using HTTP. But there is a fundamental limitation when we need extremely fast, continuous interaction.

HTTP request/response communication is like sending individual letters. Your phone asks a question, the ESP32 responds, and that exchange finishes.

WebSockets change the architecture. Instead of repeatedly creating separate requests, the browser establishes a persistent connection and both sides can send messages whenever they need to.

Today we're opening that permanent communication tunnel.

MY BRO@QUANTUM_CORE:~$ build --project ESP32-33-WebSockets
> HTTP polling → persistent WebSocket connection
> phone → ESP32 → phone
> REAL-TIME CHANNEL: ONLINE
We're going from:

"My phone has to ask for data every time."

to:

"My phone and ESP32 have a permanent, low-latency communication channel." 😎
Important engineering correction: WebSockets do not provide literally zero latency. Network propagation, Wi-Fi scheduling, TCP processing, browser processing, and application code all still take time. The important advantage is that after the connection is established, messages can flow continuously without repeatedly creating a new HTTP request/response exchange.

// 2. WEBSOCKET EVENT HANDLER
// ============================================================

void webSocketEvent(
uint8_t num,
WStype_t type,
uint8_t * payload,
size_t length
) {

```
// We only care about text messages.

if (type == WStype_TEXT) {

    // Convert incoming bytes into a String.

    String message = (char*)payload;


    // Did the phone send TOGGLE?

    if (message == "TOGGLE") {

        // Flip the software state.

        ledState = !ledState;

        // Apply that state to the physical LED.

        digitalWrite(LED_PIN, ledState);


        Serial.println(
            "⚡ Instant Toggle Received!"
        );


        // Send the new state back to every
        // connected WebSocket client.

        if (ledState == true) {

            webSocket.broadcastTXT("ON");

        } else {

            webSocket.broadcastTXT("OFF");

        }
    }
}
```

}

Hint: With INPUT_PULLUP, an unpressed button reads HIGH and a pressed button reads LOW. Detect the transition from HIGH → LOW.
C++ — CORE IDEA 
const int BUTTON_PIN = 14;
```

int lastButtonState = HIGH;

void setup() {
pinMode(BUTTON_PIN, INPUT_PULLUP);
}

void loop() {

```
int currentButtonState = digitalRead(BUTTON_PIN);

if (lastButtonState == HIGH &&
    currentButtonState == LOW) {

    webSocket.broadcastTXT(
        "PHYSICAL BUTTON PRESSED!"
    );

    delay(50);
}

lastButtonState = currentButtonState;

server.handleClient();
webSocket.loop();
```

}
```
Why the 50 ms delay? This is the same beginner-friendly debounce shortcut you've already seen. It briefly blocks the loop. It is acceptable for this tiny demonstration, but a production real-time system should use non-blocking debounce based on millis() so network processing isn't unnecessarily paused.
12 // DEBUGGING

Troubleshooting

❌ Page loads, button does nothing

Check the browser WebSocket status. Make sure the JavaScript connects to:

JavaScript 
ws://ESP32_IP:81/

The normal webpage is on port 80, while the WebSocket connection is on port 81.

❌ Compile error involving WStype_t

Make sure PlatformIO installed:

links2004/WebSockets

Other WebSocket libraries can have different APIs and callback signatures.

❌ WebSocket disconnects

Check Wi-Fi signal strength, router behavior, and whether the ESP32 remains connected.

Also avoid long blocking operations inside loop().

❌ UI says NOT CONNECTED

The browser has not successfully established the WebSocket connection yet.

Verify that the phone can reach the ESP32 IP and that port 81 is available on the local network.

❌ LED doesn't respond

Check:

  • LED polarity.
  • D2 wiring.
  • Common GND.
  • 220–330Ω series resistor.
  • Whether another circuit is already using D2.

❌ Challenge feels delayed

Look for long delay() calls.

The WebSocket stack needs the loop to run frequently so webSocket.loop() can process incoming and outgoing traffic.

Core debugging rule: If your network code appears frozen, inspect blocking code first. A long delay or slow operation inside the main loop can prevent the communication handlers from being serviced frequently enough.
13 // NEW LANGUAGE

New Vocabulary

WebSocket
A protocol that provides a persistent, full-duplex communication channel over a TCP connection.
Latency
The delay between an event occurring and the resulting response being observed.
Full-Duplex
Communication where both endpoints can send and receive independently over the same connection.
Persistent Connection
A communication connection that remains open so multiple messages can travel without establishing a completely new connection for every message.
Event-Driven
A programming architecture where actions occur in response to events such as messages, button presses, or sensor changes.
Broadcast
Sending a message to all connected clients rather than targeting only one specific client.
Port
A logical endpoint used by network services to distinguish different applications or services on the same device.
